## 一句话结论

P11 第一切片：**「取一道题」不再读整份文件**。十万题的库上从 **389ms 降到 1ms**；
第二切片：**「搜一个词」不再扫全表**，从 **613ms 降到 50ms**；
第三切片：**复核候选不再一行开一次文件**，同一条路径从 **50ms 降到 5ms**
（317 个候选，317 次开文件 → 5 次）。三次都是同一次运行里的对照，不是两次采样比。

做法不是换数据库，而是先让端口长出能力：存储层多了一个可选的「按字节读一段」，
题库目录旁多了一张**题号 → 行位置**的旁注索引。索引是派生数据 ——
丢了、旧了、被改坏了都不影响正确性，只影响下一次要不要重建。
这一刀同时把「加一道题」里最后一趟全量读拿掉了：**226ms → 26ms**。

SQLite 这一步仍然没上，原因写在最后一节（本机拿不到任何依赖）。

## 1. 端口先长语义：`RandomAccessText`

`TextStorage` 只会「整份读 / 整份写」，所以"取一道题"必然要把 49.9MB 读成字符串再逐行扫。
新增的是能力本身，不是索引格式：

```kotlin
interface RandomAccessText {
    fun byteLength(name: String): Long?
    fun readRange(name: String, offset: Long, length: Int): String?
}
```

- 只有真文件后端实现得了（桌面 / Android 的 `FileTextStorage`）；
- 内存与 Web 后端**不假装拥有**这个能力，`locate` 自动退回整份读 + 扫描，结果一致、只是慢；
- 偏移是 **UTF-8 字节**，不是字符：一个汉字三字节，按字符算出来的偏移 `seek` 过去会读到半个字。

## 2. 索引长什么样

`banks/<bankId>/offsets-v1.tsv`，一行一条，与题目文件同序：

```
q-000001	0	512
q-000002	512	509
```

十万题约 **2.1MB**（题目文件 49.9MB，约占 4%）。刻意不是 JSON：十万行三列，解析器越薄越好。

它在三条路径上生成：整库写入（导入 / `save`）时顺手排出来、追加一道题时**只追加一行**、
以及校验不过时从题目文件重建。

## 3. 三道锁：索引可以错，但不能被当成真数据

索引是派生数据，风险不是"丢了"（丢了就重建），而是**撒谎**——指到一个错位置，然后被人当真。

| 锁 | 判据 | 不成立时 |
|---|---|---|
| 结构锁 | 最后一条的结束位置 == 题目文件字节长度 | 重建 |
| 条数锁 | 解析出的条数 **不超过**目录里的题数（多出来 = 文件里有目录不知道的题） | 重建 |
| 内容锁 | 按索引读回来的那一行，`questionId` 就是要找的那个 | 这一库的索引结果全作废，重建后退回扫描 |

"一次图谱刷新查两三道题"里，任意一道触发内容锁，本次查询就老老实实扫一遍 ——
结果是**这次慢、下次不慢**，而不是快但可能错。

条数锁为什么用"不超过"：文件里若有读不懂的行，重建出来的条目天然少几条；要求相等
会让这种库**每次**定位都重建一遍 —— 把一个数据问题变成了性能悬崖。反过来"多出条目"
不能接受：那说明文件里有目录还不知道的题。

内容锁还有一条分寸：题号对得上、内容却不成形（缺选项之类），算「这一道用不了」，
不算「索引撒谎」。否则每次定位都会触发一次重建。

重建时也不收"半截行"：`{"questionId":"q-1","type":"sing` 这种崩在写一半的残行，
从行首字段里能抠出一个像样的 id，但它不是一道题；收进索引就会让每次校验都失败。
判据很便宜 —— 整行以 `}` 结尾才算写完。

## 6. 代价与边界（别把它读成"存储层已经行了"）

- **搜索 50ms 是卡在验收线上的**（目标 ≤50ms）。它由两部分构成：候选求交（几毫秒）+ 逐行读回解码。
  候选多而命中少时最慢（"第 100000 题"要验掉 300 个候选才碰到那一道）。
  再往前要做的是"一次读一段连续字节、在缓冲里切行"，那需要端口先长出按字节读块的能力。
  → 第三切片已经做了（第 10 节）：同一件事换了个做法，5ms。
- **单字查询仍然扫全表**（"题"这种）。1-gram 的 postings 与题量成正比，几个高频字就能让索引翻倍，
  所以单字段不参与挑候选，只参与最后复核 —— 拿不到候选就退化成老路径。结果一样，只是 613ms。
- **倒排表的体积高度依赖题库内容**：这次基准的十万题题干几乎一样（只差题号），索引只有 2.4MB（5%）。
  真实题库措辞各异，二元组会更分散，体积更大 —— 这一条本文件没有实测数据，不做外推。
- **改题 / 删题仍是整库重写**（`save`）。定点改写一行需要"等长替换或重排偏移"，
  这一刀没做 —— 现在删掉中间一行，后面每一个偏移都会变。
- **整库写入多了一次排索引**：重写整库 603ms → 681ms（十万题）。这是导入/导入补丁的代价，
  摊到整个导入流程里不显眼，但它确实不再免费。
- **第一次定位要 83ms** 解析索引。之后靠内存缓存（最多 2 个库）；换库会重新解析。
- **索引不是免费**：占题目文件的 4%；整库写入多一次编码（为了知道每行几字节）。
- **Web / iOS 走老路径**：它们没有随机读实现（Web 用内存存储，重启即丢），
  `locate` 仍是读整份 —— 行为一致，只是慢。
- **备份不含索引**：恢复之后第一次定位会重建（一次整份读），这是有意的。

### 另一个真事故：磁盘被自己的基准写满

跑第三轮十万题基准时报 `IOException: 磁盘空间不足`，C 盘 0 字节可用。
根因不是代码：每个基准用例都会 `createTempDir` 造一份 50–100MB 的题库，
**跑完不删**，一天几次就攒到 2.1GB（198 个目录）。现在每个基准用例收尾都会删掉自己的目录
（`cleanup(root)`），清理失败也不影响结论 —— 它只是缓存。

## 7. 为什么 SQLite 仍然没上

这次不是优先级问题，是**拿不到依赖**：

```
repo1.maven.org            连不上
dl.google.com/dl/android/maven2  连不上
github.com                 连不上（TLS 握手失败）
本地缓存                   sqlite-jdbc / SQLDelight / Room 一个都没有
```

三个候选方案（Room KMP、SQLDelight、各平台原生驱动包一层）都需要新增依赖，一个都拉不下来。
硬扛的做法是自己写一个存储引擎 —— 那比现在这套索引复杂得多，也更可能出错。

所以这一刀走的是**SQLite 之前必须先做完的那一半**：端口长出语义（`locate` / `searchQuestions`
早已是一等操作，这一刀补的是"按位置读"），并让文件实现先把能拿到的收益拿到手。
真要换库时，`BankRepository` 的实现换掉即可 —— 索引表对应一张 `(id, offset)` 的表，
内容锁与结构锁退化成 SQLite 自己的约束。

## 9. 第二切片：倒排表（搜索 613ms → 50ms）

### 9.1 长什么样

`banks/<bankId>/search-v1.tsv`，第一行是头，之后一个词一行：

```
#ktsearch 1 <生成时题目文件字节数> <生成时行数>
以下	1,1,3,1,1
说法	1,1,3,1,1
```

- 词是**二元组**（`以下说法` → `以下`/`下说`/`说法`），因为中文没有空格；
- 值是该词出现的**行号**，用 delta 编码（十万题时多半是 `1`，一行两字节）；
- 行号用的就是偏移表那套槽位号 —— 两边必须同一次扫描、同一套"这行读不读得懂"的判定。
  不同源的后果不是慢，是把别人的题当成命中交出去。

十万题（题干高度重复）实测 **2.4MB**，是题目文件的 5%（偏移表 4%）。

### 9.2 追加时为什么不重排

改倒排表意味着改十几个词的位置 —— 而我们的存储层只会"整份写/追加一行"，没有定点改。
所以追加一道题时**主索引不动**，这一行的词记进 `search-tail-v1.tsv`（一行约 60 字节）：

```
100000	10,00,第1,1题,...,以下,下说,说法
```

查询时先查主索引求交，再把尾巴逐行过一遍（尾巴通常几十行）。尾巴超过 64KB 时，
**下一次追加**顺手重排一次 —— 把一次整份扫描摊到几百次追加上。

### 9.3 三道锁，与偏移表同源但不同判据

| 锁 | 判据 | 不成立时 |
|---|---|---|
| 长度锁 | 当前文件字节数 **不小于**索引里记的那个 | 重建（文件变短 = 被改写过） |
| 行数锁 | 偏移表的条数 **不小于**索引里的 slots | 重建 |
| 记账锁 | 偏移表比索引多 N 行时，尾巴里得至少有 N 行 | 重建 |

第三条是这个设计的关键：没有它，"另一个进程往文件里追加了一行"会让那一行**永远搜不到**，
而界面上看不出任何异常。有了它，那种情况会被识别成"主索引没吸收这一行"，重建一次。

内容锁在搜索里是天然的：候选行必须真的包含完整的查询词（[matchesQuery]），
二元组交集给出的假阳性会在这里被丢掉。

### 9.4 两条路径共用一套判据

`matchesQuery` 同时被"索引路径"和"扫描路径"调用。这不是为了省代码 ——
是因为两条路径**必须给出同一批题**：用户在桌面上搜到的东西，换到 Web 端（没有随机读能力）
必须一模一样。`indexAndScanPathsReturnTheSameQuestions` 就是拿六个查询逐条对照这件事。

### 9.5 写这份代码时撞到的三个坑

1. **delta 的第一条是 0**：行号 0 编码成 `0`，而 `0` 在解析侧是"这张表坏了"的信号（行号必须递增）。
   结果是自己写出来的索引自己读不回来。修法：起点从 -1 算起。
2. **标点不是词边界**：一开始把"以下，说法"里的逗号换成空格，于是它和"以下说法"切出不同的
   二元组 —— 用户搜"以下说法"找不到那一行，一个逗号决定了命中与否。现在标点直接丢掉，只有空白算边界。
3. **多读 2KB 兜底的代价**：候选行按索引里记的精确长度读就够了，多读 2048 字节让搜索的读取量
   从 158KB 变成 632KB，耗时从 50ms 变成 54ms —— 而它能挡的那种情况（长度偏小）本来就只会
   导致解码失败、少一条命中，不会给出错答案。

另外，第一版还试过给单字也建索引（想让"第 1 题"里的"1"能搜到），体积直接翻倍；
改成"单字不参与挑候选、只参与复核"，索引减半，代价是全单字查询走扫描。

## 10. 第三切片：候选复核成批读（搜索 50ms → 5ms）

### 10.1 钱花在开文件上，不在读字节上

第 9 节最后一行已经点到了：50ms 里，读的字节只有 158KB，剩下的全是**开关**。
一个候选一段、一段一次 `open/seek/read/close` ——"第 100000 题"有 317 个候选，就是 317 次开关。
索引把"该读哪几行"算对了，钱却还花在原地：**读得准，但读得太碎**。

这一刀没有新增文件格式、没有新增锁，改的是"怎么读"，不是"读什么"。
所以第 9 节那三道锁一句都没动，两条路径（索引 / 扫描）共用的 `matchesQuery` 也没动。

### 10.2 端口再长一条能力：`readSpans`

```kotlin
fun readSpans(name: String, spans: List<TextSpan>): List<String?>   // 下标一一对应，读不到是 null
```

- 默认实现就是循环 `readRange`：**结果一样，只是多开几次**。内存 / Web 后端用这条 ——
  它们本来就没有句柄可省，"批量"对它们是无意义的话；上层不必知道自己拿到的是哪一种。
- 真文件后端（桌面 / Android 的 `FileTextStorage`）整批共用一个句柄，并把挨得近的段
  （下一段的起点不超过当前末尾 4KB）并成一次读。合并阈值刻意小：并进来的字节也要解码，
  "省一次 seek"的收益抵不过把整片文件读进来。

段边界仍然只落在行首（偏移来自偏移表），所以**每段单独解码**不会切在半个汉字上 ——
`RandomAccessTextTest.batchReadMatchesReadingEachSpanOnItsOwn` 就是拿中文 + emoji 的题核对这一条。

### 10.3 批次是"停车距离"

复核候选必须保住"凑够上限就停"：`limit = 5` 时不该读十万行。整批读会破坏这一点，
所以批次是 **64 行**：最坏比上限多读 63 行（约 32KB），而一次文件打开能摊到这 64 行上。

代价在"高频词"那一格看得见：查询几乎命中每一行时，它只要 5 条，却读了 64 行 —— 4ms → 6ms。
**这是这一刀唯一变慢的地方**，换的是稀疏查询从 317 次开文件变成 5 次。这个交换是划算的：
稀疏查询是交互里真会卡人的那一条（图谱填一个端点、搜索点进去），
而多读 32KB 在这台机器上是 1–2ms。

### 10.4 数字（本次运行：100000 题 / 51188895 字节）

| 阶段 | 耗时 | 数据量 | 说明 |
|---|---|---|---|
| 对照：搜一个词（读整份 + 全表扫描） | 391ms | 48.8MB | 无随机读能力时走这条（Web / 内存后端） |
| 索引搜索·第一次 | 77ms | 2.4MB | 解析该库倒排表；之后留在内存里 |
| 索引搜索·之后（**成批读候选**） | **5ms** | 162284 字节 / **读盘 5 次** | 317 个候选，每次摊 63 行（每行约 500 字节） |
| 高频词（候选十万行，只验证 5 条） | 6ms | — | 唯一变慢的一格（4ms → 6ms），原因见 10.3 |
| 定点取题·之后 | 1ms | 512 字节 | 未受影响（走 `readRange`，一次一段，本来就是对的） |
| 追加一道题 | 12ms / 写 787 字节 | — | 未受影响 |
| 重写整库（`save`） | 523ms | 48.8MB | 未动：仍是整库重写（见第 8 节第 2 条） |

口径要说清楚：本次运行的"对照"是 391ms，第 9 节那次是 613ms —— **同一条扫描路径**，
两次之间磁盘缓存状态不同（这一轮所有对照都快：定点取题 389ms → 217ms）。
所以 50 → 5 不能全记在成批读头上；把对照的差异折算过去，成批读本身大约压掉这一步的**四分之三**。

不随机器状态变的是**结构**：317 个候选 / 5 次开文件。改回逐行读，那个 5 立刻变成 317，
`SearchIndexTest.verifyingManyCandidatesReadsThemInBatchesNotOneOpenPerLine` 会红。
这就是为什么这一条的验收判据是"向存储要了几次字节"，不是"跑了几毫秒"。

### 10.5 这一刀踩到的两件事

1. **越界的段不能吞掉整批**。批里有一段算过界（文件短了、索引偏了），正确做法是那一段 null、
   其余照读；写成"任何一段失败就返回空列表"的后果不是慢，是**整个搜索返回空**，
   而界面上看不出任何异常 —— 用户会以为题库里没有这个词。
2. **合并相邻段之后必须按字节切片，不能按字符切片**。合并读回来的是一整块 `ByteArray`，
   每一段要拿 `offset - blockStart` 去切；先解码成 String 再切字符，就等于假设
   "字节偏移 == 字符下标"，中文一律错位，而且错得很安静（还是能解码出文字，只是不是那一行）。

### 10.6 边界

- **只有真文件后端省得下这笔钱**。Web / 内存后端走默认实现（每段一次 `readRange`），
  行为与数字都还是第 9 节那一列 —— 它们本来就没有句柄可省。
- **批次大小是个折中，不是最优解**。真要榨干，可以让批次随"已读行数"增长（8 → 16 → 32 → 64），
  高频词那 1–2ms 就能省回来；但那是为两毫秒加一层状态，暂时不做。
- **一次搜索仍然要读回 317 行**。候选多、命中少时，真正的上界是"候选数"，不是"次数"。
  再往前只能让索引带上更多信息（例如把题干原文放进倒排表），那是拿磁盘换 IO，还没算过账。
