### 十万题实测（本机 JVM，`KT_BENCH=1`）

| 阶段 | 耗时 | 数据量 | 驻留堆 |
|---|---|---|---|
| 生成 100000 题 NDJSON | 67ms | 19715 KB | 45 MB |
| 导入解析 | 767ms | 19715 KB | 111 MB |
| 写入题库 | 783ms | 49989 KB | 111 MB |
| 重新打开（只读目录） | 8ms | 0 KB | 6 MB |
| 取题面（触发整库解析） | 622ms | 49989 KB | 95 MB |

口径：每步 `System.gc()` 后量驻留堆；导入与重载分处两个作用域，量的是"只有一份题库在内存里"的状态。
机器为 Windows + JDK 21，数字只作量级参考，不作为验收阈值（测试里不写死耗时）。

## P5 第五切片：跨题库知识图谱与缺失依赖恢复（2026-10-20）

P6 的四项里，图谱与"缺失依赖恢复"是同一块基础：`.qbext` 的跨库硬依赖也要复用这套引用模型，
所以先把它落地，再接扩展包格式。

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| 跨库引用 | ✅ | `domain/graph/KnowledgeGraph.kt`：以 `bankId + questionId` 定位，**只存引用不复制正文**。作者改题后图谱跟着看到新内容，不会留一份会过期的副本 |
| 四种关系 | ✅ | `RELATED / PREREQUISITE / EXPLAINS / CONTRASTS`，方向统一读作「source ——关系—— target」；对称关系（相关/对比）明确标为无方向 |

## P6 第一块：`.qbext` 扩展包（2026-10-20）

图谱跑通之后，扩展包几乎是它的另一半：图谱解决「我自己连」，扩展包解决「作者连好了发给我」。
两者共用同一套引用模型（`ExtensionRelation.toGraphEdge`），所以扩展包带来的关系进图谱后，
和手工建的走完全相同的状态判定与缺失恢复。

核心定位：**扩展包只往本机加两样东西 —— 跨库关系与讲解注释，题库本体一个字都不改。**
机制上也不允许改：包里根本没有题目结构，只有 `relations/` 与 `annotations/`。

## P7 第二块：批量生成队列（持久化 · 暂停/继续/取消 · 次数上限）（2026-10-20）

单题生成解决的是"这道题为什么是这个答案"；接着暴露出来的是另一个问题：
**一个两百道的库，难道要我一题一题点？**

但"批量"这件事一旦做错，代价比单题大两个数量级 —— 点错一次就是两百次请求。
所以这一块的重点不在"能跑批"，而在**每一条规则都能让账单可预期**。

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| 先排后跑 | ✅ | "排进队列"只建清单、**一次请求都不发**；"开始"才动手。两个按钮分开，用户才有机会在扣费前看一眼总数 |
| 排队列即算清 | ✅ | 建队列时就排除"已有讲解 / 没有该语言题面 / 超出单任务上限"三类并报数，不是跑起来才发现 |
| 已有讲解不重复花钱 | ✅ | 按 `bankId+questionId+locale+修订+内容指纹+模型` 命中缓存即排除；扫描用一次 `records()` 建索引，不逐项查文件 |
| 一次只发一个请求 | ✅ | 不做并发。并发会让预算瞬时超限、服务端 429、错误混在一起分不清哪道是限流 |
| 失败不重试 | ✅ | 失败项标 `FAILED` 并继续下一道。100 道 × 3 次重试 = 300 次请求，这在计费接口上是事故 |
| 失败也计数 | ✅ | `attempts` 记 1，因为失败同样发了一次请求；不记的话"反复点开始"就能绕过上限 |
| 预算不足 → 暂停 | ✅ | 每日次数 / token / 费用任一不够时**暂停整个任务**，剩余项保持待处理。把剩下 40 道标成失败，用户会以为题库坏了 |
| 本次次数上限 | ✅ | 用户可设"这次最多问几道"（默认 50，0 = 不限）。到上限暂停，不标失败，随时可再排 |
| 暂停在请求边界 | ✅ | 点暂停不打断正在飞的请求 —— 打断同样扣费，还会留下一条不知道算成功还是失败的记录 |
| 取消保留成果 | ✅ | 取消只把任务标 `CANCELLED`，已生成的讲解一条不删，未处理的项也没被清空 |
| 进度可续跑 | ✅ | 每个任务存清单 + 游标；`run` 从游标继续，已完成的项不再发请求 |
| 进度不靠任务文件保证 | ✅ | 讲解记录每道都落盘，任务文件节流写（每 5 项）。中途被杀最多丢 5 项游标，重扫后那几道会被标成"跳过"，不会重复付费 |
| 继续前重扫 | ✅ | 暂停期间用户可能单独生成过几道，继续前重扫一次，不为它们再花一次钱 |
| 题目改动按新内容生成 | ✅ | 执行时从题库取**当前**题目重新组请求，不用建队列时的快照；快照只用于判断"题目还在不在" |
| 题目消失 → 跳过 | ✅ | 题库被删 / 题目没了 / 没有该语言题面，都标 `SKIPPED` 并写原因。标失败会让用户去查网络 |
| 配置坏了立刻停 | ✅ | 未同意上传 / 密钥被删时第一步就暂停，不在同一份错误配置上重复失败几十次 |
| 任务持久化 | ✅ | `ai-batches-v1.json`：清单、状态、游标、本次上限、说明。重开应用还在，可继续 |
| 坏文件不覆盖 | ✅ | 整份解析失败按空处理且**不写回**（里面是用户排好的待办）；单个任务不完整只跳过并计数 |
| 只留最近 20 个 | ✅ | 完成的是记录不是档案；清理时**未结束的任务一律保留** —— 清掉等于偷偷删了用户的待办 |

### P7 第二块已知限制

- 单任务上限 500 道：超出时截断并报数，需要用户再排一个 —— 没有"分页队列"或"自动接力"

## P7 第一块：AI 讲解（按需生成 · 预算 · 审核）（2026-10-20）

题库这边能"给人看什么"已经够用了，剩下一个真实缺口：**这道题为什么是这个答案**，
教材里没写、作者也没留解析的时候，只能自己去别处查。

定位：**AI 是可选的一层，不是基础功能的一部分。** 没配置、没同意上传、超预算时一次请求都不发；

## P8 第一块：`.qbpatch` 题库更新补丁（2026-10-20）

一句话：**作者能说清"我基于第几版改了什么"，应用端能核对"这份补丁是不是给我这一版的"，
用户能在按下按钮之前看见"会改哪几道题、哪几道题的答案变了、那些题我练过几次"。**

补丁与"重新导入一份新 `.qbank`"的区别只有一条：**后者会覆盖，前者会交代。**
所以这一块的重心不在"能改"，而在三件容易糊过去的事 —— 改得对不对（锚点）、
该不该改（判定顺序）、改完历史怎么办（一条不动）。

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| KT-QBP 1.0 容器 | ✅ | `knowledge-trainer-bank-patch`：`manifest.json`（含 `baseRevision` / `targetRevision` / `baseFingerprint` / `patchId` / 可选 `title`） + `operations` 数组 + 可选媒体。与 `.qbank` / `.qbext` 同一套"清单 ↔ 条目双向 sha256"纪律，错一条整包拒绝 |
| 制包工具（零依赖） | ✅ | `tools/qbank/qbpatch.py build / validate / fingerprint`。`build --base old.qbank` 从**旧包**算锚点并给每条操作补 `expect`；作者不用手写任何指纹。示例产物 `examples/starter-v2.qbpatch`（v2.0.0，第 1 版 → 第 2 版，新增 1 / 修改 2 / 删除 0） |
| 指纹两侧同源 | ✅ | `ktqbf/fingerprint.py` 逐字节复刻 Kotlin 的算法（FNV-1a 64，16 位十六进制；题目集合指纹是**逐项相加**模 2^64，见 P10 第 21 节），只做这一件事；`FingerprintParityTest` 用 golden 值锁住两侧（`827015e596399cd3` / `q001=7a946af22e6b29e0` 等）。**当初把它写成 64 位十六进制，工具算出的指纹被自己拒绝**，是这条测试之后才不再复发 |
| 两个锚点 | ✅ | 库级 `baseFingerprint`（整库内容指纹，即"哪一版"）+ 题级 `expect`（该题当时的指纹，即"你手里那条还是我改的那条吗"）。库级锚点回答"要不要改"，题级锚点回答"能不能改" |
| 读取器 | ✅ | `QbpatchImporter`：`op` 白名单（add / update / remove）、同一题只能有一条操作、`update` 的 `set` 只允许 8 个字段、`add` 的新题必须过 `QuestionRules`（多选题一个答案这种当场拦下） |
| 纯函数应用器 | ✅ | `BankPatcher.apply(bank, patch)` 无 IO、无副作用，返回 `Ok / NoOp / Outdated / Failed`。合并后**再复检一次**整题合法性 —— 改完变成"多选题只剩一个答案"的补丁会被拒绝，而不是写进题库 |
| 判定顺序 | ✅ | ① 身份与内容都对不上 → `BANK_MISMATCH`；② 库级指纹匹配 → 严格应用，逐条校验 `expect`；③ 不匹配 → 宽松重算（不校验 expect），结果与本地一致 → `NoOp`；④ 仍失败且冲突只有 `EXPECT_MISMATCH`/`PATCH_NO_EFFECT` → `NoOp`；⑤ 否则比版本号 → `Outdated` / `CONTENT_DIVERGED` / `BASE_MISMATCH`。**顺序是这套东西里唯一不能随便动的部分** |
| 幂等 | ✅ | 同一个补丁再装一次：`NoOp`（"这些改动早就在了"不是错误）。`PATCH_NO_EFFECT` 是**好消息**，界面照实说"不需要更新"，不弹红色报错 |
| 改不了什么 | ✅ | `update` 不许改题型与判题策略：题型一变，"什么算答对"和历史口径同时变，那是"换了一道题"。要换就 `remove` + `add`，让它在预览里显眼 |
| 历史一条不动 | ✅ | 应用补丁只写两处：题库文件 + 修订日志。作答记录属于历史，补丁没有资格重写它。`affectedAttempts` 只**统计**"答案变更的那几道题你练过几次"，不改任何一条记录 |
| 答案变更单列 | ✅ | `PatchReport.answerChanges` 与 `contentChanges` 分开；界面把"答案变更"放在统计数字**之前** —— 反过来排，用户会先看到一个漂亮的"共 3 处改动"，然后在长列表底部才发现自己练过三次的题答案被改了 |
| 修订日志 | ✅ | `bank-revisions-v1.json`：只存**摘要**（新增/修改/删除数、答案变更题号、影响历史条数、作者备注），不存旧题目全文 —— 它的用途是回溯"改过什么"，不是回滚。同一修订号覆盖而非并列；整份损坏时先另存 `.corrupt` 再重写 |
| 两步落地 | ✅ | `intake` 只读（解析 + 定位 + 试算），`apply` 才写。`apply` 不相信预览结论：重新定位、重新应用一遍 —— 用户可能在两步之间装了别的补丁 |
| 定位顺序 | ✅ | **先按内容指纹，再按 bankId**。早期导入会重新生成 UUID，那些库的 ID 与作者声明的不一致；只按 ID 找，老用户永远收不到更新 |
| 导入身份改为包声明 | ✅ | `QbankImporter` 现在读 `manifest.bankId` 与 `contentRevision` 并沿用，不再每次导入新生成 UUID；同一 bankId 内容不同 → `ImportOutcome.IdentityConflict`，提示"请用 `.qbpatch`"，**不静默覆盖**。1.0 包里没有 `bankId` 的仍可导入（现场生成一个），代价见已知限制 |
| 界面 | ✅ | `PatchScreen`：拒绝 / 找不到目标库 / 待应用三态；待应用里再按 `Ok / NoOp / Outdated / Failed` 分支，`Failed` 逐条列冲突码与中文原因。首页题库卡新增"第 N 版"徽章（只在 `contentRevision > 1` 时显示 —— 给一辈子停在第 1 版的库挂个版本号只是噪声） |

### P8 第一块已知限制

- **补丁只能一版一版打**：从第 1 版直接跳到第 3 版要连装两个补丁，没有"累积补丁"或"跨版合并"
- **不能改题型、判题策略、题库语言集合**：前两者是 `update` 显式禁止（请用 remove + add），语言集合则根本不在补丁能碰的范围内
- **没有 GUI 制包**：只有命令行 `qbpatch.py`，作者要会写 JSON
- **没有签名**：逐文件 `sha256` 只保证"传输没坏、没被改过"，不保证"作者是谁"。来源仍只记文件名
- **修订日志不能回滚**：它只记摘要，不存旧题目正文。想退回上一版只能重新导入完整包
- **没有 bankId 的老包只能靠内容定位**：内容一旦被本地改过，补丁就既认不出它、也不能按 id 找到它 —— 用户会看到"找不到要更新的题库"。修法是让作者在新版包里补上 `bankId`，再用完整包覆盖一次
- **答案变更后旧历史不重算**：界面告诉你"哪几道题的答案变了、你练过几次"，但重判本身由用户发起 —— 见下一节「P8 第二块：用户控制的历史复核」
- **删除的题仍留在历史里**：历史指向已不存在的题目，错题本与统计里表现为"关联已失效"，不做级联删除
- **预览与落盘之间没有锁**：`apply` 会重算，所以不会写坏；但如果两步之间题目被别处改过，用户看到的是"补丁和本地对不上"，需要重新打开补丁再看一遍

## P8 第二块：用户控制的历史复核（2026-10-21）

一句话：**答案改了，软件不替用户重判过去，也不假装什么都没发生 —— 把差异摆出来，一条一条问。**

这一块补的是上一块留的那个口子。上一块说"历史一条不动"，但只做到一半：
历史确实没被改写，可用户手里多了一批"按现在的标准看，判定是错的"记录，却没有任何出口。
现在的做法是**把判断权交回去**：谁都不该替别人决定"你当时那次作答算不算数"。

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| 找差异的依据 | ✅ | **不看修订日志，看重算结果**：把每条记录按当时的作答输入重新判一遍，与记录里的判定不一致就成为候选。理由很实际 —— 触发原因不止补丁：作者发新版包、用户手工改题、跨两个版本装补丁都会改内容；只信日志会漏掉后两种 |
| 候选带什么 | ✅ | 现在的题干、题型、题库标题、"当时判的 X"、当时的作答（按**那次冻结的显示顺序**翻成 A/B/C）、"按现在重算 Y"、现在的标准答案。要不要复核是一个判断题，只给"判定变了"没法判 |
| 什么不算候选 | ✅ | ① 判定没变；② 放弃的作答（本来就没有判定）；③ 只是选项顺序变了（判题按 optionId，打乱顺序不是"答案变了"，否则每次 shuffle 都会造出几十条假待办）；④ 已经就**同一版内容**表过态 |
| 两种决定 | ✅ | 「按新答案复核」= 采用重算判定；「维持当时判定」= 保留原判定。**两条路都写一条决定** —— 只记"接受"，会让"我看过了，不改"变成每次打开都要重看一遍 |
| 决定只追加 | ✅ | `attempt-reviews-v1.ndjson` 一行一条，同一条历史以**最后一条**为准。推翻上一次决定也是追加一条，"我改过主意"本身要可查 |
| 判断依据会被记住 | ✅ | 每条决定带 `basisFingerprint`（复核时题目的内容指纹）。题目再改一次，依据变了，旧决定的前提就没了 —— 这条历史会重新出现在待复核里 |
| 不改写历史文件 | ✅ | 复核结果**只在读取时合并**：`AttemptReviews.apply` 返回副本，`verdict` 换成生效判定，原判定留在 `review.from`。`attempts-*.ndjson` 一个字节都不动 |
| 派生状态自动跟上 | ✅ | 统计、正确率、错题本、日历全部从合并后的 `history` 派生，**没有改一行**。复核完正确率立刻变，错题本立刻多出/少掉那道题 |
| 逐条与批量 | ✅ | 逐条两个按钮；批量「全部按新答案」/「全部维持当时判定」。批量也走弱按钮 —— 一下就改几十条数字的动作，做得太顺手反而是问题 |
| 没有主按钮 | ✅ | 整页一个 `PrimaryButton` 都没有，两个选项视觉等重。这里不存在"推荐答案"：接受会动统计，维持会让你以后再做这道题时口径不一致，哪个更对取决于用户怎么看那次作答 |
| 首页只有真有事才出现 | ✅ | 工具栏「复核 N」只在 `reviewPending > 0` 时出现。这个数字只用**已经读进内存的历史 + 修订日志**算，**不解析题目** —— 首页刷新不该为了一个徽章去读十万道题；真正的差异等点进页面再算 |
| 进页面才扫描 | ✅ | `reviewPlan = null` 表示未扫描，`openReview()` 才起协程重算。`refresh()` 只把上一份清单作废（题库变了，旧清单就不可信） |
| 题目没了的记录 | ✅ | 单独计入 `ReviewPlan.unreviewable` 并在页面上报数，**不混进候选、也不悄悄少列**。它们做不了复核（没有可重算的题面），但历史里一条都没少 |
| 痕迹可见 | ✅ | 首页最近提交里标「复核改判」/「复核保留」；历史页多一行"当时判 X，你按新答案改成了 Y"。判定与当时不一致却看不出为什么，比不改还糟 |
| 重算不信任界面 | ✅ | `decide()` 重新 `plan()` 一遍再写 —— 用户可能在看列表和点按钮之间又装了个补丁 |
| 跨语言按当时的语言重算 | ✅ | 用记录里的 `locale` 取题面（缺译文退回原文），与历史页显示同一份题面。两处各写一遍回退链，迟早出现"历史页显示英文、复核却按中文答案判" |

### P8 第二块已知限制

- **只问"判定变了"的**：题面改了但判定不变（例如只改了错别字）不会进复核。用户可能想知道，但把每条文字改动都变成一次确认是打扰
- **只能二选一**：不能"算部分正确"或"改判成待确认"。判题策略能给出什么，就只能接受什么
- **界面上没有撤销入口**：想反悔目前只能再写一条决定（`ReviewHistoryUseCase.decide`）。底层支持"最后一条为准"，缺的只是那个按钮 —— 如实记录，不假装有
- **复核不改当时快照**：`questionFingerprint`、`answerRevision`、用时、选中的选项都保持原样。它们记的是"当时那一次发生了什么"，复核只改"这次算不算对"
- **改了判定的题不会回到"未练习"**：它仍然是练过的，只是不再算错
- **大批量没有筛选和分页**：一次全部列出，不能按题库/时间范围过滤。极端情况（一次改了几百道题、每条都练过）会是一页很长的列表
- **决定文件只增不减**：反复推翻会线性增长；量级是"用户主动点过的决定"，没有做压缩
- **题库被卸载后不可复核**：那道题没有可重算的题面，只能计入"不可复核"，不能凭记录里的旧判定改判
- **批量只有"全部"**：没有"只处理这一屏"或"只处理这个题库"
- **没有跨设备同步**：决定存在本机的 NDJSON 里，与历史同源

## P8 第三块：来源真实性（2026-10-21）

一句话：**出处是作者声明，软件只能核对"包内自洽"，不能核对"内容属实" —— 所以界面上绝不把"没说"写成"原创"。**

这一块要解决的不是"能不能查到出处"，而是"**查不到的时候，界面长什么样**"。
题库软件里最危险的不是错题，是来路不明的题被当成可靠材料反复背诵。
而"作者没说"与"作者说了是原创"是两件完全不同的事，混在一起就等于替作者做了声明。

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| 题库级出处清单 | ✅ | `manifest.sources[]`：`sourceId / title / kind / author / edition / url / license / note`。`kind` 限定 book / paper / web / course / original / other |
| 题目级三种出处状态 | ✅ | `origin`（`authored` / `adapted` / `imported` / `ai-assisted`）+ `sourceId` + `sourceLocator`（章节 / 页码 / 题号）。三者都可缺省 |
| 缺省就是"未标注" | ✅ | `ProvenanceOrigin.UNSPECIFIED.label = "来源未标注"`。**不是**"作者原创"，也不是中性空白 —— 界面上有独立的一行淡灰字 |
| 拼错不猜 | ✅ | `origin: "copied"` 一律 `ORIGIN_INVALID` 拒绝，不做"最接近的那一个"。猜错等于替作者声明了他没说过的事，且事后无法从数据里看出 |
| 悬空引用整包拒绝 | ✅ | 题目引用了 `sources` 里不存在的 `sourceId` → `SOURCE_UNKNOWN`。作者删了一条来源却漏了题目，是最常见的打包错误 |
| 重复 sourceId 拒绝 | ✅ | `SOURCE_DUPLICATE`。同一个 id 指两条来源，读者无法判断该信哪条 |
| 两处"说了但没说清"只警告 | ✅ | 标了来源却没写 `sourceLocator` → `SOURCE_LOCATOR_MISSING`；声称 `imported`/`adapted` 却没有 `sourceId` → `ORIGIN_WITHOUT_SOURCE`。题本身没问题，不该拒绝 |
| 整包内容摘要 | ✅ | `manifest.contentDigest`（sha256，64 位十六进制）。应用端**重算**后比对，不符 → `CONTENT_DIGEST_MISMATCH` 拒绝导入 |
| 摘要只依赖逻辑内容 | ✅ | 输入是"身份字段 + 排序后的 `path sha256`"，与 ZIP 时间戳、压缩级别无关。同一份内容换个工具重打 → **摘要相同**（能认出"这是同一个包"） |
| 摘要覆盖什么、不覆盖什么 | ✅ | 覆盖 `format/schemaVersion/bankId/contentRevision/sourceLocale/supportedLocales/title/author/license` + 全部内容文件；**不覆盖** `sources` / `tags` / `description`（改了不该换摘要，否则"改一句说明就变成另一个包"） |
| 摘要不是签名 | ✅ | 没有密钥，任何人改完内容都能重算一个自洽的摘要。文档与界面上都这么写，不用"校验通过"这种词 |
| 旧包照常导入 | ✅ | 没有 `contentDigest` → `CONTENT_DIGEST_MISSING` 警告，`digestVerified = false`。界面据此写"未提供"，**不打勾** |
| 出处不进内容指纹 | ✅ | `Question.contentFingerprint()` 只含题型 / 题干 / 答案 / 选项内容。作者补一个漏写的出处，不会让补丁的逐题 `expect` 全部失效 |
| 补丁可以改出处 | ✅ | `update.set` 接受 `sourceId` / `sourceLocator` / `origin`；**空串表示清空**（"null = 不改，空串 = 改回没有"）。出处变更单列一类 |
| 「出处变更」是独立分类 | ✅ | `PatchChangeKind.PROVENANCE`。它不换内容版本号（不白费一次 AI 讲解缓存）、不进复核清单、预览里显示"来源未标注 → 改编自 甲教材 · 2020 · 第二章" |
| 只改出处不会被静默丢弃 | ✅ | 上一块的"变没变"只看内容指纹，只改出处的补丁会报告"没有变化"。本块改为内容指纹 **或** 出处任一变化都算改；严格模式下"每条改动都已成立"降级为 `NoOp` 而不是报失败 |
| 首页看得到谁做的 | ✅ | 题库卡第三行：`作者 · 出处 N 处 · 许可`。旧包没声明作者就不显示 —— 不写"未知作者"这种体面的默认值 |
| 做题时看得到出处 | ✅ | 题干下方一行：`改编自 甲教材 · 2020 · 第一章 第二节 课后练习 3`。位置有讲究 —— **作答之前**就该知道这道题哪来的 |
| AI 参与生成看得见 | ✅ | 琥珀色胶囊 `AI 参与生成` + 参考出处。不是警告，是让人知道"这段文字可能没经过人审" |
| 作者/许可进了存储 | ✅ | `BankProvenance` 存进题库目录（`BankMetaDto.provenance`），首页与详情不解析题目就能显示；旧目录迁移时留空，不伪造 |
| 作者自己能看见机器读到了什么 | ✅ | `validate_qbank.py validate` 多两行：`来源 N 条：原创 x / 改编 x / 引用 x / AI 参与 x；来源未标注 x；N 题指向具体来源` 与 `内容摘要=…`；`inspect` 也列 `contentDigest` 与来源书名。`--json` 多出 `contentDigest` 与 `provenance` 两段（老包无出处时 `provenance` 整段不出现，避免被读成"标了 0 处"） |

### P8 第三块已知限制

- **出处无法验证真伪**：软件能核对"包内引用自洽"，不能核对"这本书第 42 页真有这道题"。作者写什么就是什么 —— 这一块的诚实全在界面上：它从不把声明说成证明

- **摘要不覆盖 `sources`**：改了来源说明不会换摘要。理由是它属于"说明性元数据"，但代价是"作者偷换出处"这个场景查不出来
- **`AI 参与生成` 靠作者自报**：应用无法检测一段文字是不是模型写的。这个字段的作用是"让认真的作者能标注"，不是"自动识别"
- **界面上没有出处详情页**：只能看到一行摘要，点不开。`url` / `note` 读进来了、存下来了，但还没有地方展示全文
- **编辑器不能改出处**：手工新建的题永远是"来源未标注"，只能通过重新导入或补丁来标。这是下一步的活
- **补丁只能逐版**：与 P8 第一块同样的限制 —— 跨两个版本要连打两次
- **旧包一律"未标注"**：升级前导入的题库没有出处信息，迁移时留空。它们看起来和"作者忘了写"完全一样，因为数据上确实一样

## P9 第一块：`.qbk` 备份与恢复（2026-10-21）

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| `.qbk` 容器 | ✅ | ZIP：`backup-manifest.json` + `data/<原路径>`。清单记 `format / backupVersion / layoutVersion / createdAt / deviceLabel / appVersion / encrypted / files[] / counts / contentDigest` |
| 为什么和 `.qbank` 分两套格式 | ✅ | 装的不是一回事：题库包是"一个库的内容，给别人"，备份是"整台机器的全部数据，给自己"。共用 ZIP 与 sha256，其余各管各的 |
| 手写 ZIP 写入器 | ✅ | `ZipWriter` 只写 **STORED**（不压缩）：common 里只有解压器，引入压缩器换来的只是体积小一点。CRC32 自己算，时间戳固定 1980-01-01，文件名标 UTF-8 → **同数据打两次字节完全相同**（两台的摘要才对得上） |

### P9 第一块已知限制

- **备份没有加密**（第一块时点）：能打开这个文件的人能看到全部题目与笔记。加密已在 P9 第二块补上，见下节
- **只有桌面端能做**：Web / iOS 的数据在内存里，没有可备份的东西；Android 还没有"保存到用户选的位置"的通道。这两处都如实说明，不给点了没反应的按钮
- **全量进内存**：一次备份要把所有数据读进内存再压成 ZIP，上限 2 GiB。十万题的库 + 大量图片时内存占用可观
- **不压缩**：备份文件 ≈ 原始数据大小（含 ZIP 头开销）。换来的是不用引入压缩器、恢复时不需要解压器
- **不做合并恢复**：只能整体替换。想"把两个机器的数据合起来"只能先恢复再导入题库 —— 合并出一种既不是备份也不是本机的状态，比不合并糟
- **旧数据目录占磁盘**：恢复后旧数据被改名留在旁边（这是退路），下次恢复才清。磁盘紧张时要手动删
- **只备份应用自己的数据**：用户自己导出的 `.qbank`、桌面上的文件不在范围内
- **单文件上限 50 MiB**：沿用 `ZipReader` 的限制。单个题库的 NDJSON 超过这个数（约八十万题）就无法备份
- **恢复会连"进行中的练习"一起换掉**：`session-v1.json` 也在数据里。如果备份来自另一台机器，恢复后首页可能出现那台机器的"未完成"卡片 —— 这是原样搬过来的结果，不是 bug
- **摘要不是签名**：能发现"文件被截断/改过"，防不住"有人改了再给你"

### P9 第二块已知限制

- **KDF 是 PBKDF2，不是 Argon2id**：抵抗离线爆破的能力取决于口令本身；显卡批量猜 PBKDF2 比 Argon2id 便宜。界面上直说"四个不相关的词比一个复杂但短的词更牢"，不给假装客观的强度条
- **口令没有找回方式**：这是加密的定义。软件不存口令、不存提示、不留后门；忘记就只能放弃那份备份
- **没有做密钥文件 / 硬件密钥**：口令是唯一入口，一个字符串被看到就等于备份被打开
- **明文信封泄漏统计**：能看到"这份备份里有 3 个题库、12 条历史、来自某台机器、什么时候导出的"。文件名、摘要、内容都不在里面
- **加密备份上限 64 MiB**：纯 Kotlin GHASH 约 20 MB/s。更大的数据请用不加密的备份（上限 500 MB）
- **不是抗侧信道实现**：S 盒是查表，缓存计时理论上可观测。它防的是"别人拿到文件"，不防"别人在你机器上跑计时攻击"
- **没有对 ZIP 层做认证**：GCM 保护的是载荷；ZIP 结构本身（条目名、顺序）可以被改，只是改坏了就解不开。密文条目的名字是固定值，改它等于找不到载荷
- **一次只能解锁一份**：换了文件或取消都要重输口令（重新派生 600000 轮 ≈ 0.6 s）
- **恢复仍是整体替换**：产品总纲提到的"恢复冲突合并"没有做。这里选择"确认 + 旧数据留在旁边"，理由见 P9 第一块：合并出一种既不是备份也不是本机的状态，比不合并更糟


## P9 第三块：恢复中断可自愈（恢复日志 · 启动修复）（2026-10-23）

| 能力 | 状态 | 说明 / 证据 |
|---|---|---|
| 恢复日志写在数据目录**外面** | ✅ | `<数据目录名>.restore-journal.json` 与数据目录同级。最危险的瞬间数据目录恰好不存在 —— 日志放在它里面，那一刻就没有任何东西能说明"发生了什么" |
| 日志用行格式，不用 JSON | ✅ | 首行 `kt-qbk-restore-journal 1`，后面 `key=value`。这份文件是崩溃之后唯一还能解释磁盘状态的东西，字段顺序/缩进/转义任何一处漂移都会让它在关键时刻读不出来；而它只由本类写、只由本类读 |
| 日志原子写 | ✅ | 先写 `.tmp` 再 rename —— 半个日志比没有日志更坏：它会让人以为恢复停在了一个根本没到过的阶段 |
| 两个阶段 | ✅ | `STAGING`（还没碰数据目录，任何情况都能回滚）→ `SWAPPING`（从这一行起数据目录可能不存在）。`SWAPPING` 写在"移走旧目录"**之前**，所以"数据目录还在"永远等于"旧数据还在" |
| 日志记下 `hadRoot` | ✅ | 恢复开始前数据目录在不在。没有它，"本来就没有数据（新机器）"和"数据不见了"分不开，而这两件事该说的话完全不同 |
| 启动自愈：六种现场 | ✅ | 回滚（清半成品）/ 退回旧数据 / 前滚（接上新数据）/ 已经完成只差收尾 / 数据不见了 / 日志读不懂。判定表写在 `DirectoryVault.recoverInterrupted` 的注释里，测试逐个构造这些现场 |
| 前滚要先验完整性 | ✅ | 半成品必须"文件数与总字节都对得上日志"才允许接上去，否则一律退回旧数据。残缺的新数据比旧数据更糟 |
| 自愈只收拾半成品 | ✅ | 旧数据目录、日志指向的目录一律不动（除了把它改名为正式目录）。"顺手整理"别人的退路，是恢复功能最不该做的事 |
| 自愈不抛异常 | ✅ | 它站在启动路径上，抛出去等于应用起不来。真出错就返回 `RECOVERY_FAILED`，界面照实说"什么都没敢动" |

### P9 第三块已知限制

- **只能检测并修好，不能保证零丢失**：如果断电正好发生在"rename 已生效、日志还没写下去"的那一瞬，靠的是"现场本身可分辨"（数据目录在或不在），而不是日志 —— 这也是日志必须记两个阶段、且 `SWAPPING` 先于 rename 写下的原因
- **自愈只在启动时跑一次**：运行中数据目录被外部删掉，应用不会当场发现（下次启动才会）
- **恢复日志不加密**：里面有数据目录名、文件数、总字节数；没有文件名，也没有任何内容
- **没有"撤销上一次恢复"按钮**：退路是把 `*.pre-restore-*` 手工改回原名，界面只给路径。做成按钮要处理"撤销到一半又断电"，那是另一块工作量
- **只覆盖恢复的中断**：导入、装补丁的中断仍是"失败即不落盘"（它们没有"一次性换掉整个目录"这个动作，不需要日志）
- **前滚依赖半成品还在**：用户手工删掉 staging 之后只能退回旧数据（回滚永远比前滚安全）

### P9 第四块已知限制

- **只查"指向的东西在不在"，不查"指得对不对"**：关系建错了对象、把 A 题的前置写成 B 题，自检看不出来
- **不检查内容本身**：题干写错、答案标错、笔记里有错别字，都不是它的事
- **媒体只核对文件在不在**：文件被换成另一张图、或者被截断，字节对不上它也发现不了（那需要逐文件摘要，属于备份容器的职责）
- **文件清单依赖平台**：Web / iOS 的数据在内存里，`listPaths()` 给不出清单 → 图片一项跳过并明说"没有核对"
- **题目存在性按库建索引**：十万题的库第一次被查时要摊平一次全部 `questionId`。自检本来就是这个量级，但它不是 O(1)
- **面板只列前 5 个目标 / 5 张图**：总数照实写，明细要看完得点进对应页面（图谱页、笔记页）
- **不提供"一键清理指空引用"**：题目级的指空引用是用户自己建过的东西，自动抹掉比留着更糟

## 已知限制（如实记录，不假装完成）

| 限制 | 说明 |
|---|---|
| 纯 Kotlin inflate 性能 | 约为原生 zlib 的 1/3，几十 MB 题库无感，更大需评估 |
| JS / Wasm / iOS 文件选择 | `FilePicker` 未接入，界面明确提示不可用并给出替代路径（桌面端导入 / 粘贴 JSON / 桌面拖拽） |
| JS / Wasm 自动化测试 | 沙箱无外网，karma 依赖下载失败；Inflate 纯 Kotlin 无平台 API，JVM 金标准测试可代表四端行为 |
| 媒体持久范围 | Web / iOS 的媒体仓库为内存实现，重启丢失（与文本存储同警告）；桌面 / Android 落盘于存储根目录 `media/` |
| 拖拽导入实测 | 代码级验证 + 全目标编译通过；未做真实拖放操作实测（沙箱无法模拟 OS 拖拽） |
| 增强资料使用 | 只做结构与审核状态校验，练习中不消费（`ENHANCEMENT_IGNORED` 警告） |
| 存储层仍是文件 | 目录 + 每库 NDJSON，不是 SQLite：没有随机访问与增量索引。十万题可以（重开 8ms），但"读进内存"仍要 622ms / 95MB |
| 单库题目常驻内存 | 一场练习会把该库整库解析进内存，没有按页取题。十万题约 95MB —— 桌面端可以，移动端偏重，几十万题必须换成分页读取 |
| 写库是整文件重写 | 单库十万题一次写 50MB；改一道题也要重写整个库文件。行级写入要等数据库层 |
| 导入分两段遍历 | 解析（校验 + 预览）与写入各走一遍，内存里同时存在题目对象与原始文本。真正的"暂存区 + 批量事务"要等数据库层 |
| 富文本不是完整 CommonMark | 只实现题库会出现的子集：无表格、无引用式链接、无 HTML、无嵌套列表；不支持的 Markdown 语法按原文显示 |
| 数学排版不是 TeX 引擎 | 无连字/字距微调、无 `\begin{align}` 对齐、无自定义宏；`\left(` 超过 3.4 倍时封顶缩放（极端高公式会略矮）。渲染与求值严格分离：**不做任何数学等价判题**，简答题仍是逐字符比对 |
| 富文本不可选中 | 含公式的段落走 Canvas 自绘，无法用鼠标选中复制（纯文本段落仍是普通 `Text`，可选中） |
| 笔记不参与判题 | 笔记只是个人记录，不进入抽题、不影响错题判定与统计 |
| 笔记引用不做级联删除 | 题库或题目不存在时，笔记仍保留并标注"关联已失效"——宁可留一个指向失效的索引，也不静默删掉用户写下的文字 |
| 笔记无导入导出 | 目前只有本机 `notes-v1.json`；跨设备迁移笔记尚未提供（题库可重新导入，笔记不行） |
| 计算器只做数值求值 | 不解方程、不化简、不保留分数与根号的精确形式（`1/3` 显示 0.3333333333）；不做数学等价判题，简答仍是逐字符比对 |
| 计算器记录不持久化 | 只在内存里留最近 20 条，关掉应用即清空；这是刻意的定位（它算一个数，不是笔记本） |
| 单位表是人工整理的 | 收录 82 个学习常见单位，不是完整换算库（无光年、无市制斗/升、无 Mach）；系数按定义或法定值写，`CONVENTION`/`APPROXIMATE` 会在界面上标注 |
| 工具使用只记录不干预 | `usedTools` 写进历史并在反馈里标注，但不影响判题、不参与统计口径；"正式测试禁用工具"尚未实现 |
| 图谱关系靠手工 | 没有自动推荐、没有相似题挖掘、没有导入导出。这是刻意的：结构正确的自动连线读起来很像事实 |
| 判题硬依赖目前只是"声明" | 现有判题策略不读跨库资料，所以"暂停"体现为明确标注与不把缺失依据当理由；真正消费跨库资料的策略要等扩展包（`.qbext`）与对应判题器 |
| 图谱只按内容版本判断变化 | `contentRevision` 是作者声明的契约；作者改了内容却忘了升版本，软件看不出来。没有文本指纹兜底 |
| 关系数量未分页 | `graph-v1.json` 整文件读写，几千条关系无压力；上万条需要分页或换 SQLite |
| 扩展包不能改题库 | 只有 `relations/` 与 `annotations/`，改题干、补答案、加选项一律做不到 —— 这是刻意的：一个能改题库的"补丁"会在下次重装题库时被静默抹掉 |
| 扩展包不看题库版本 | 绑定的是 `bankId`，不是题库版本。作者按 v1 写的关系，装到改了题的 v2 上照样生效，可能指向已不存在的题（会显示 `MISSING_QUESTION`，但不会被提前拦下） |
| 扩展包无签名 | 只有逐文件 `sha256` 保证"传输没坏、没被改过"，**不保证作者是谁**。没有签名链、没有发布者身份校验，来源只记文件名 |
| 扩展包关系不可就地编辑 | 图谱编辑器里点编辑会跳回扩展包页。改一条就得重制整包：包是作者的单向声明，本机改动会在下次装包时被覆盖 |
| 扩展包无 GUI 制包 | 只有命令行 `qbext.py`。作者要写 NDJSON —— 面向的是会写 JSON 的人 |
| 注释不参与判题 | 与笔记同理：讲解只是给人看的，不影响抽题、判题、统计 |
| 软件界面只有中文 | 这一块做的是**题库语言**（题面/选项/答案）多语言；界面文案本身仍是硬编码中文。"界面语言、题库语言、作答语言三者独立"只实现了后两者 |
| 语言标签只支持三段 | `language[-Script][-REGION]`；变体（`-1996`）、扩展（`-u-ca-...`）、私有段一律拒绝，而不是解析后忽略 |
| 不做语言/地区模糊匹配 | `en` 与 `en-US` 是两种语言，`zh-Hans` 与 `zh-CN` 也是。同语种回退只在候选唯一时发生 |
| 译文不能逐字段混用 | 译文缺任一选项即视为"没有这一份"（宁可整题原文）。代价是译者必须整题译完才能生效 |
| 无翻译编辑界面 | 应用内不能补译文，只能重制包再导入；界面编辑器只写源语言 |
| 无机器翻译 | 不内置翻译、不调用任何翻译服务；AI 翻译进个人扩展属于 P7 |
| 语言学习题未做语言锁定 | "题干语言固定、只考目标语言作答"这类模式未实现：现在题干与答案同属一种语言 |
| 每语言统计只到抽题范围 | 历史与错题本可**按语言筛选**，但首页总览、日历、正确率曲线仍是全语言合并；没有"按语言分开的统计报表" |
| 进度与历史仍不跨设备 | 与笔记同理：`banks/`、`attempts`、会话都在本机 |
| 复核只能二选一 | 「按新答案」或「维持当时」，没有"算部分正确"、没有手工指定判定。判题策略能给什么，就只能接受什么 |
| 复核没有撤销入口 | 底层支持"同一版内容以最后一条决定为准"，但界面只有逐条/批量的两个方向按钮，想反悔得再点一次反向操作（清单里已经看不到它了）。缺的是"查看已复核记录"的列表 |
| 复核扫描是整表重算 | 进页面时把**全部历史**逐条重判一遍，没有增量索引。万条历史在桌面端无感，移动端会明显卡一下；分页或"只扫最近 N 天"还没做 |
| 复核不做筛选与分页 | 候选一次全部列出，没有"按题库 / 按时间"过滤，也没有批量只处理一屏 |
| 复核结论不改当时快照 | `questionFingerprint`、`answerRevision`、用时、选中选项保持原样 —— 记录的是"当时发生了什么"，复核只改"这次算不算对" |
| 复核以原始作答重算，不重演当时的判题器 | 用的是**当前**的策略实现（例如 keywords 规则后来改过判法，就按新判法算）。所以复核结果反映的是"现在的标准"，不是"当时那版代码的标准" |
| 出处不可验证 | 只能核对"包内引用自洽"，不能核对"内容真出自那本书"。作者写什么就是什么 |
| 内容摘要是防手滑不是防篡改 | 无密钥、无签名：改完内容重算一次摘要就自洽了。能发现"忘了重新打包"，防不住"故意改过" |
| 摘要不覆盖来源与标签 | 改 `sources` / `tags` / `description` 不换摘要（避免"改一句说明就变成另一个包"），代价是"偷换出处"查不出来 |
| AI 标注靠作者自报 | 应用不检测文字是否出自模型；这个字段只让认真的作者能标注，不做自动识别 |
| 出处只显示一行 | `url` / `note` 已读入并存储，界面还没有可展开的详情页，也点不开链接 |
| 出处不能在编辑器里改 | 手工新建的题永远是"来源未标注"；要标只能重新导入或走补丁 |
| 备份只能整体替换 | `.qbk` 恢复是"把本机换成那台机器"，没有合并。旧数据改名留在旁边，但不会把两边的历史拼在一起 |
| 备份加密默认关闭 | 默认加密会让"备份完了却打不开"成为最常见事故；关掉开关时文件谁拿到谁能看，页面上用琥珀块固定说明 |
| 加密口令不可找回 | 没有提示问题、没有密钥文件、没有后门；KDF 是 PBKDF2（不是 Argon2id），抗爆破能力取决于口令本身 |
| 加密备份上限 64 MiB | 纯 Kotlin GHASH 约 20 MB/s；更大的数据只能用不加密的备份（解压总量上限 500 MiB） |
| 加密时明文信封仍泄漏统计 | 别人能看到"几个题库、几条历史、来自哪台机器、何时导出"；文件名与逐文件摘要都在密文里 |
| AI 密钥仍明文存本机 | `.qbk` 的口令保护不覆盖本机密钥文件；能读到这台机器的文件的人仍能读到密钥 |
| 只有桌面端能备份 | Web / iOS 的数据在内存里，关掉就没了；Android 还没有"保存到用户选的位置"的通道。这两处只写原因，不摆点了没反应的按钮 |
| 恢复中断只能"修好"，不能"零丢失" | 恢复全程记日志，断电/被杀之后下次启动会回滚或前滚；但断电正好落在 rename 与写日志之间时，靠的是现场本身可分辨，不是日志 |
| 自愈只在启动时跑一次 | 运行中数据目录被外部删掉，应用不会当场发现，下次启动才处理 |
| 没有"撤销上一次恢复"按钮 | 退路是把 `*.pre-restore-*` 手工改回原名，界面只给路径；做成按钮要处理"撤销到一半又断电"，是另一块工作量 |
| 引用自检只判"在不在" | 不判"指得对不对"：关系建错了对象、把 A 题的前置写成 B 题，它看不出来。它扫的是引用闭包，不是语义 |
| 引用自检不检查内容 | 题干写错、答案标错、笔记有错别字都不在它的范围里。页脚那句"不做内容校验"是给它的 |
| 缺图只核对文件名存在性 | 不比对字节：文件被换成另一张图或被截断，自检发现不了（逐文件摘要是备份容器的职责） |
| 自检结果不落盘也不进备份 | 每次重新算。一份备份里的"结论"是导出那一刻的判断，而用户是恢复之后才看它，中间可能已经装了别的题库 |
| 自检面板只列前 5 个目标 / 5 张图 | 总数照实写；完整明细要进图谱页、笔记页看。大量缺口时不做分页，也不提供"一键清理" |
| 自检查题的索引按库摊平 | 每个库第一次被查时要把全部 `questionId` 收进一个 `HashSet`。十万题的库会为自检多占一份 id 集合 |
| 给不出文件清单的平台跳过图片检查 | Web / iOS 的 `listPaths()` 返回 null，面板写"图片没有核对"；不把"不知道"当成"一张都没有" |
